Section 1 · Product

The cloud half of an offline-first system

The Android app never needs a server — but shops with connectivity get multi-device sync, per-store analytics APIs, and a feed for the Streamlit dashboard. One Django codebase serves all three, with PostgreSQL in production and a zero-setup SQLite file for development.

Stack

Django >=4.2, DRF >=3.14, psycopg[binary] >=3.1. Python 3.10+. No Celery, no Redis — boring and dependable.

Tenancy

Every business row carries a store FK. API-key callers can only ever see their own store; cross-store access returns 404, never 403-with-a-hint.

App compatibility

Field names mirror the Room entities, epoch-millis timestamps are accepted, and endpoint shapes match exactly what data_pipeline/fetch_data.py consumes.

Run it

cp .env.example .env then ./start.sh — migrates and serves at http://127.0.0.1:8000. Postgres via docker compose up -d db.

CRUD plus bulk upsert

EndpointWhat it does
GET /products/Store-scoped list with ?search=, ?category=, ?low_stock=1 filters, paginated.

Section 6 · The money path

Idempotent by invoice number

POST /sales/ accepts one sale, a bare list, or {"sales": […]} with nested lines. Replays return the existing record (200, no double stock decrement) instead of duplicating it.

  • Mobile-native timestamps — FlexibleDateTimeField accepts epoch millis, epoch seconds and ISO-8601.
  • Line linking — matches catalog products by Android id, then barcode; unlinked lines still store with their names.
  • Stock decrement — linked products lose the sold quantity, floored at zero, inside the same DB transaction.
  • Atomicity — sale header + lines + stock move together; partial writes are impossible.

Section 7 · Reads

Section 8 · GET /analytics/summary/

Per-store numbers, server-computed

One call returns everything the owner dashboard needs; accepts the same ?since= / ?days= window as the listings.

totals

revenue, orders, avg_ticket, vat_collected, gross_profit, margin_pct — ORM aggregates, rounded to 2 dp.

payment_mix + top_products

Revenue/orders/share per method; top 5 items by revenue with units sold.

low_stock

Count plus the 50 emptiest items, each with a suggested reorder qty (2 × threshold − stock).

inventory_value

SUM(cost × stock) across the catalog.

Section 10 · Running it

SQLite today, Postgres tomorrow

Local dev

No POSTGRES_* vars → local db.sqlite3. ./start.sh creates the venv, installs, migrates and serves. --no-server migrates only (CI); --reinstall rebuilds the venv.

Production DB

docker compose up -d db starts Postgres 16-alpine with a persisted volume; set the four POSTGRES_* vars and re-run ./start.sh.

Admin + health

Django admin covers all four models (sales show inline lines). GET /health/ is the load-balancer check — no auth required.

Secrets

.env, db.sqlite3 and .venv/ are git-ignored; only code, docs and .env.example commit.

Section 12 · Contract

Built to feed the dashboard

data_pipeline/fetch_data.py was verified live against this API: register → product → sale → analytics, then a full pipeline fetch + analyze run.

  • List responses use DRF pagination (results key), which the fetcher already unwraps — alongside bare lists and data/items wrappers.
  • Snake-case fields map onto Room columns (the fetcher is case/underscore-insensitive); line items additionally carry transactionId / productId aliases.
  • Timestamps serialize as ISO-8601, which the fetcher parses alongside epoch millis/seconds.
  • Point the pipeline at it with SAJILO_API_URL=http://127.0.0.1:8000 + the store key.
